1. 实验2-3 发现，滑动窗口对话历史会导致Agent反复执行相同的工具调用。但完整保留历史又会让上下文不断膨胀。设计一种策略，既能避免信息丢失，又能控制上下文长度，且不破坏KVCache前缀
   外部完整归档 + 结构化状态 + 分阶段追加上下文
    工具结果存入文件，上下文只保留摘要和路径；同一阶段内，只追加，不改写；使用显式状态；

2. 
2.1 Qwen3 的 Chat Template 思维链保留机制只保留“最后一个真实用户消息之后”的思考。如果一个 ReAct 循环跨越了上百轮工具调用，累积的思考内容可能消耗大量上下文。你会如何修改这个机制来应对超长循环？
引入检查点边界；用执行状态代替旧思考 
2.2 DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部reasoning_content——对比这两种相反的策略，各有什么利弊？这个反转说明了什么？
v4 为了agent时代能够更好连续工作，因此选择保存之前的思考内容；R1则偏向于每轮独立思考，可能是更多的出于成本考虑

3. 上下文感知压缩实验中，从约 148K 个字符压缩到约 2,000 个字符，这种极端的压缩是否存在“不可逆信息损失”的风险？如何解决？
存在，可以将原文写入文档并记录摘要和引用，需要时可回查复原。同时单独保存关键约束和执行状态，防止重要信息被省略。

4. Agent 状态栏将隐式状态显式化。但如果状态栏本身包含了错误信息（比如工具计数器出了bug），Agent 可能基于错误的信息做出有害的决策。这种“元信息可靠性”问题如何缓解？
由于状态栏都需要通过代码来维护，因此可以在代码中实现：状态栏元信息附上版本、时间和来源；用一致性检查发现错误。agent 侧：高风险决策由执行层核验，不能只看状态栏

5. 提示工程消融实验表明，信息组织的混乱导致成功率下降30% 以上。但在实际开发中，系统提示词往往由多人在不同时间维护。你会用什么工程实践来防止系统提示词的“熵增”？
把系统提示词当作有结构、有测试、有负责人维护的**代码资产**。
固定结构 + 明确适用范围和优先级 + 版本控制与负责人审核 + 自动检查与回归测评 + 定期清理

6. 本章提出“上下文学习本质上是检索而非推理”。如果这个论断成立，当前所有基于“把更多信息塞进上下文”的优化方向都需要重新审视。你认为应该如何突破这一局限？
把信息获取和问题求解分开，通过知识库、语义检索等手段，仅在需要时去检索相关的信息；将复杂任务转换为可沉淀复用的流程步骤，确定性逻辑由代码控制、不确定性的则交给模型。

7.  Skills 的渐进式披露只在 Agent 判断需要时才加载完整内容。但这个判断本身依赖模型的能力——如果模型不知道自己不知道什么，就无法正确触发Skill的加载。这个“元认知”问题如何解决？
让系统承担路由和披露职责。常驻的skill虽不是完整文件，但是desc中需要有清晰的职责、触发词、用于解决的问题等；系统在每次加载可以按规则出发，比如文件扩展名、工具类型等

8. Skills 机制中，Agent 从 SKILL 文件中动态读取提示词之后，后续的操作能否正确遵从这些指令？不同的模型对Skills 模式的支持有什么区别？
未必能严格遵守。skill的设计需要严谨：要求写得可执行、可检查；确定性操作交给脚本，关键约束交给执行层；记录留档，可随时复盘检查

9. 本章强调动态信息（如系统时间戳、工具列表顺序）的变化会破坏KVCache前缀命中。在一个拥有大量工具且工具集频繁变动的生产系统中，你会如何设计上下文布局来最大化缓存命中率？
工具库与提示词分离，将大量工具存放在外部注册表，仅暴露稳定入口工具（比如search_tool, invoke_tool, get_tool_shcema等），模型通过主动search来发现工具；
工具定义使用固定版本，阶段内尽量不变；
动态内容仅追加，不覆盖前文。
